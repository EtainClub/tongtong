## 0. 한 문장

**되고 싶은 것(직업·학위·창업)을 정하면, 그 길 위의 언제 어떤 정부 정책을 쓸지 시간축에 배치하고, 정책과 내 사정이 바뀔 때마다 고쳐 가는 살아있는 설계도.**

지금의 통통은 "이 정책이 뭐지?"(카드 한 장)에 답한다. 청사진은 "내 길에서 이 정책은 **언제** 쓰는 거지?"(정책 여러 개의 순서·겹침·빈칸)에 답한다.

| | 카드 (지금) | 청사진 (새로) |
|---|---|---|
| 단위 | 정책 한 개 | 목표 하나 + 정책 여러 개 + 시간 |
| 질문 | 이게 사실인가, 좋은 정책인가 | 내 길에서 언제·무엇을 쓰나, 겹치거나 빠진 건 없나 |
| 사용자가 남기는 것 | 판단(신뢰·평가) | 계획(배치·상태) |
| 시간 | 카드 버전·90일 재평가 | 몇 년 단위 시간축 + REV |
| 재료 | 카드 | **정책 항목** (2장) |

## 1. 도장에서 가져오는 것과 바꾸는 것

도장의 청사진은 "되고 싶은 사람의 삶의 방식 → 습관"이다. 통통의 청사진은 "되고 싶은 것 → 정책 이용 경로"다. 뼈대는 같고, 재료와 바뀌는 이유가 다르다.

| 도장 | 통통에서 | 이유 |
|---|---|---|
| Legend 청사진(도감) → Fork → REV.1 | **경로 견본**(운영자가 쓴 `paths`) → 가져오기 → REV.1 | 백지에서 시작하지 않게. 견본은 카드처럼 git에 두고 검수한다 |
| REV 버전 + 구조화 변경 로그(`designIntent`, `changes[]`), LLM 없는 diff | 그대로 | 실패·변경을 "놓침"이 아니라 "REV.4: 예비창업패키지 → 다음 해로"로 남긴다 |
| 개정 제안은 주간 리뷰 주기로만, 결정권은 사용자 | 개정 제안은 **사건이 생길 때**(정책 개정·신청 기간·나이 상한) 결정론으로. 결정권은 사용자 | 바뀌는 계기가 습관 기록이 아니라 정책 쪽에서 온다 |
| 습관 = 매일 실천 단위 | **배치**(placement) = 정책 하나를 내 길의 한 시점에 놓은 것 | 매일 체크하는 앱이 아니다. 몇 달에 한 번 행동한다 |
| 활성 청사진 상한 1개 | 같음 (`MAX_ACTIVE_BLUEPRINTS = 1`) | 초점. 상한 숫자만 올리면 "박사 vs 취업" 비교가 열린다 |
| LLM 4곳, 나머지는 결정론 | LLM은 **초안 제안·청사진 질의** 2곳, 둘 다 claim grounding | 통통의 AI 원칙(검토 5.4) — 목록에서 고르게 하고 서버가 검증한다 |
| 복셀 캐릭터·먹(재화) | 가져오지 않는다 | 통통은 무채색·데이터에만 색. 혜택을 게임 점수로 만들지 않는다 |

## 2. 콘텐츠 두 층 — 정책 항목과 카드

### 2.1 왜 나누나

청사진은 정책이 많아야 쓸모가 있다. 그런데 지금 카드 한 장은 훅·숏츠·게임·판단 흐름·이유 목록·비판·검증된 claim이 다 있어야 공개된다. 이 무게로는 박사 경로 하나를 채우는 데도 몇 주가 걸린다.

청사진이 정책에서 필요로 하는 것은 그중 일부다 — 누가(나이·학적), 언제(회차·반복), 얼마나 오래, 무엇과 함께 못 받는지, 무엇이 먼저인지, 근거와 신청처. 그래서 **정책의 사실은 가벼운 정책 항목(policy entry)에 두고, 카드는 그 위에 따져보기 경험을 얹는 층**으로 나눈다.

| | 정책 항목 (새로) | 카드 (지금 카드에서 경험 부분만) |
|---|---|---|
| 위치 | `src/content/policies/*.ts` | `src/content/cards/*.ts` |
| 담는 것 | 이름·한 줄 요약, 대상(`audience`·`category`·`lifeStages`), claims·sources·counterpoints, `policy`(이력·신청 회차), `planning`, `revisions`, `reviewedAt`, `links` | `policyId`, 훅·숏츠, `flow`, 게임, `reveal`, `reasonOptions`, `suggestedQuestions`, `tone` |
| 공개 조건 | 모든 claim 검증, 출처 1개 이상 (`planning`은 경로 견본에 넣을 때 필수) | 항목이 공개 상태 + 지금의 카드 공개 조건(비판·한계 1개 이상, 이유 3개 이상) |
| 쓰는 곳 | 청사진 배치·점검·질의, 정책 페이지(`/policy/{id}`) | 피드, 카드 흐름, 따져보기 |
| 만드는 품 | 원문 대조 위주 | 무겁다 (훅·게임·이유 설계) |

### 2.2 규칙

1. **사실은 한 곳에만.** 카드는 claim을 갖지 않는다. 게임 정답·`reveal`·이유 근거가 가리키는 claim id는 모두 그 카드의 항목에 있어야 한다(`validateCard`가 항목과 함께 본다). 정책이 개정되면 항목 하나만 고친다.
2. **카드 하나 = 항목 하나.** 항목에는 카드가 없거나 하나 있다. 항목 id와 카드 id는 같은 슬러그를 쓴다 — 기존 카드는 그대로 같은 id의 항목이 된다.
3. **버전은 항목이 가진다.** `revisions`는 사실의 개정 이력이라 항목으로 옮긴다. 카드 버전 = 그 항목의 마지막 revision. 기존 카드의 `revisions`를 그대로 옮기므로 저장된 판단의 `cardVersion`, "새 정보" 배지, 재평가가 깨지지 않는다. 훅·게임 문구 같은 카드 경험 수정은 사실이 아니라 버전을 올리지 않는다(지금도 material이 아니다).
4. **앱 코드는 거의 그대로.** `src/content/cards/index.ts`가 항목 + 카드 경험을 합쳐 지금과 같은 `Card` 타입을 만든다(`resolveCard`). 피드·카드 화면·판단 API·AI 따져보기·집계는 바뀌지 않는다.
5. **승격.** 청사진에 많이 놓이는 항목, 빈칸 요청이 많은 항목부터 카드로 만든다. 청사진이 카드 제작 우선순위를 알려 준다(9.4).
6. **항목에는 판단이 없다.** 신뢰·평가를 묻지 않으니 비판·한계가 공개 필수는 아니다. 대신 "정부 홍보로 읽힘" 위험은 경로 견본의 `caveats`(출처 필수)와 항목 화면의 "공식 공고로 다시 확인하세요"로 막고, 비판·한계가 있으면 항목 화면에 함께 보인다(10장).

### 2.3 항목 스키마

```ts
policySchema = z.object({
  id,                                   // 카드가 있으면 카드와 같은 슬러그
  publishStatus: z.enum(["draft", "published"]).default("draft"),
  audience, category, lifeStages,       // 지금 카드에서 옮김
  name: z.string(),                     // 지금의 shortTitle
  summary: z.string(),                  // 한 줄. 사실만, 과장 없이 — 훅이 아니다
  claims, sources,
  counterpoints: z.array(claimSchema).default([]),
  policy: { history, applications },    // 지금 카드에서 옮김
  planning: planningSchema.optional(),  // 4.4. 경로 견본에 넣으려면 필수
  revisions, reviewedAt, links,
})
```

### 2.4 정책 페이지 `/policy/{id}`

카드가 없는 항목에도 보여 줄 곳이 있어야 한다. 화면은 단순하다 — 이름·요약, 조건(claim 칩), 신청 회차와 상태, 기간·함께 못 받는 정책, 비판·한계(있으면), 출처, 공식 신청처, 정정 요청. 카드가 있으면 머리에 `[따져보기]`로 카드 흐름에 보낸다.

- 들어오는 곳: 청사진의 배치 시트, 청사진 "+ 정책 넣기" 목록, 주제 페이지 아래 "카드가 아직 없는 정책" 묶음, sitemap(공개 항목).
- 피드에는 넣지 않는다. 피드는 넘겨보고 따져보는 곳이라 카드만 둔다.

### 2.5 판단 순서와 부딪히는 곳

카드는 "판단 전에 근거를 먼저 보이지 않는다"(로드맵 M4)를 지킨다. 그런데 정책 페이지·배치 시트는 같은 정책의 사실을 바로 보여 준다. 사실을 먼저 본 사람의 첫 판단(훅 신뢰)은 오염된다.

- 규칙: **카드가 있는 항목의 정책 페이지를 열면** 그 사실을 본 것으로 기기에 기억한다(`seenFacts`, localStorage — 판단 값이 아니고 서버에 보내지 않는다). 청사진에 놓은 항목도 본 것으로 친다.
- 그 사용자가 나중에 카드를 열면 훅 신뢰 단계를 건너뛰고 게임부터 시작한다. 첫 판단 지표(M8 "첫 판단 도달률")에 섞이지 않는다.
- 정책 페이지의 `[따져보기]`는 "이미 내용을 봤으니 훅 판단은 건너뛰어요" 한 줄과 함께 보낸다.

## 3. 원칙

1. **정책은 항목에서만 온다.** 청사진에 놓을 수 있는 정책은 `src/content/policies`에 있는 항목뿐이다. AI도, 견본도 항목 밖 정책을 만들지 않는다. 항목이 없는 필요는 "아직 등록되지 않은 정책"으로만 보이고 사실을 말하지 않는다.
2. **확정과 예상을 나눈다.** 항목의 `applications`에 있는 날짜는 확정, 과거 회차에서 미룬 날짜는 예상, 아무 근거가 없으면 미정. 화면에서 셋을 다르게 그린다(5.3). 몇 년 뒤 계획은 대부분 예상이다 — 그걸 숨기지 않는다.
3. **자격을 판정하지 않는다.** "받을 수 있다"가 아니라 "이 시점에 조건이 맞을 가능성 / 확인 필요". 최종 판정은 신청 기관이다 (검토 3장 5번).
4. **청사진은 의견이 아니다.** 배치는 "이 정책이 좋다"는 판단이 아니다. 판단 값(신뢰·평가)으로 배치를 추천하지 않고, 배치로 판단을 추정하지 않는다 (로드맵 6장 "판단 값을 쓰는 추천" 안 함 유지).
5. **혜택을 점수로 만들지 않는다.** "총 3,240만 원 혜택" 같은 합계, 달성률, 랭킹을 두지 않는다. 금액은 정책별로만 보인다 (변화량 점수 금지와 같은 이유 — 검토 2.5).
6. **바뀌는 것이 정상이다.** 정책 개정·종료, 내 계획 변경은 실패가 아니라 REV다. 바뀐 이유가 기록에 남는다.
7. **결정론 먼저.** 점검(겹침·나이·기간·개정)은 순수 함수로 계산하고 저장하지 않는다 — 신청 상태를 날짜에서 계산하는 것과 같은 원칙 (검토 4.3).
8. **쓰기는 서버만.** 지금처럼 클라이언트는 자기 문서를 읽기만 하고, `/api/blueprint`가 `lib/blueprint`의 순수 함수 규칙을 적용해 쓴다.

## 4. 개념 모델

```
목표(Goal) ── 경로 견본(Path, 선택) ──▶ 청사진(Blueprint) REV.n
                                         ├─ 기준(Baseline): 언제 기준, 지금 단계, 나이(선택)
                                         ├─ 이정표(Milestone): 입학·졸업·석사 입학·법인 설립 …
                                         └─ 배치(Placement): 정책 항목 × 시점 × 역할 × 상태
                                                   ▲
         정책 항목(Policy) + planning ──────────────┘     카드(Card) = 항목 + 따져보기 경험
                                                   │
                            점검(Check) = f(청사진, 항목들, 오늘) ──▶ 제안 ──(사용자 수락)──▶ REV.n+1
```

### 4.1 목표 (Goal)

| kind | 예 | 비고 |
|---|---|---|
| `degree` | 이공계 박사, 석사 후 취업 | 진학 경로 |
| `career` | 개발자 취업, 기술직(자격증) 취업, 공공기관 | 취업 경로 |
| `startup` | 재학 중 창업 실험 → 졸업 후 법인 | 창업 경로 |
| `other` | 직접 적기 | 견본 없이 시작. AI 초안(B4) 또는 빈 청사진 |

목표 문장은 사용자 글이다(`title`, 60자). 목표 연도(`horizonYear`)는 기준 연도 + 최대 10년.

### 4.2 이정표 (Milestone)

사용자의 삶의 사건. 정책이 아니다. `2027-03`(월) 정밀도로 적고, 화면은 반기로 묶는다 — 몇 년 뒤를 날짜까지 적는 건 거짓 정밀도다.

예 (이공계 박사): 학부 3학년(2027-03) → 학부 졸업(2029-02) → 석사 입학(2029-03) → 박사 진학(2031-03) → 박사 수료·학위(2035-02)

### 4.3 배치 (Placement)

| 필드 | 뜻 |
|---|---|
| `policyId` · `policyVersion` | 어떤 정책을, 어느 버전 기준으로 계획했나. 항목이 개정되면 점검이 이 버전과 비교한다 |
| `milestoneId` (선택) | 어느 이정표에 딸린 것인가 |
| `from` · `to` (선택) | 쓸 기간 `YYYY-MM`. 적금처럼 긴 것은 구간, 응시료처럼 한 번인 것은 `from`만 |
| `role` | 이 길에서 하는 일: `funding`(학비·생활비) · `housing` · `asset` · `skill`(역량·자격) · `experiment`(일경험·창업 실험) · `startup`(창업 준비·운영) · `employment`(취업·근속) · `living`(교통·문화) · `safety`(공백기 안전망) |
| `status` | `planned` → `ready`(신청 준비) → `applied` → `active`(받는 중) → `done` / 갈래: `missed`(놓침) · `dropped`(뺌) · `ineligible`(대상 아님 확인) |
| `note` (선택) | 사용자 메모 200자. 소득·장애 같은 사정을 적지 말라는 안내를 둔다 |

`status`는 사용자가 바꾼다. 앱이 바꾸지 않는다 — "신청함"인지 앱은 모른다.

### 4.4 항목의 `planning` 필드

청사진 점검은 항목에 구조화된 계획 정보가 있어야 돌아간다. 모든 값은 claim을 가리킨다 — 게임 정답이 claim을 가리키는 것과 같은 원칙 (검토 4.2).

```ts
planningSchema = z.object({
  roles: z.array(PlacementRole).min(1),
  /** 만 나이 조건. 경계는 claim에 적힌 대로. */
  age: z.object({ min: z.number().int().optional(), max: z.number().int().optional(), claimIds }).optional(),
  /** 지원 기간(개월). */
  durationMonths: z.object({ value: z.number().int().positive(), claimIds }).optional(),
  /** 언제 다시 열리나 — 예상 일정의 근거. 근거 claim이 없으면 비운다 → 미정. */
  recurrence: z.object({ kind: z.enum(["once", "annual", "rounds", "always"]), note: z.string().optional(), claimIds }).optional(),
  /** 함께 받을 수 없는 정책 (중복 수혜 제한). 양쪽 항목에 모두 적는다 — validatePolicies가 대칭을 본다. */
  exclusiveWith: z.array(z.object({ policyId: z.string(), claimIds })).default([]),
  /** 이게 끝나야(또는 있어야) 쓸 수 있는 것. 예: 2단계 사업은 1단계 수료 후. */
  after: z.array(z.object({ policyId: z.string(), claimIds })).default([]),
  /** 대상이 되는 학적·단계. lifeStages보다 좁은 조건이 있을 때만. */
  stages: z.array(PlanStage).default([]),
})
```

- `PlanStage`는 `LifeStage`를 넓힌 것: `undergrad` · `grad_master` · `grad_phd` · `leave_of_absence`(휴학) · `graduated_unemployed` · `employed` · `founder_pre`(예비창업) · `founder_early`(창업 초기) · `military`.
- `validatePolicies()`(항목 사이 불변식, 새로 둠): `exclusiveWith`·`after`의 `policyId`가 존재하고, `exclusiveWith`가 대칭이고, `after`에 순환이 없다.

### 4.5 경로 견본 (Path)

도장의 Legend 청사진에 해당. `src/content/paths/*.ts`, 항목·카드와 같은 검수(`pnpm validate`).

```ts
pathSchema = z.object({
  id, publishStatus: "draft" | "published",
  goalKind, title, summary,            // "이공계 박사 진학 — 학부 3학년부터"
  startStage: PlanStage,                // 이 견본이 가정하는 출발점
  milestones: [{ id, label, offsetMonths }],   // 출발점 기준 상대 시점
  slots: [{ id, policyId, milestoneId?, fromOffset, toOffset?, role, why }],
  /** 이 경로 자체의 한계 — 기회비용, 정책이 끊길 위험. 출처가 있어야 공개. */
  caveats: z.array(claimSchema),
  sources: z.array(sourceSchema),
  revisions, reviewedAt,
})
```

- `why`는 편집자 설명 한 줄("석사 기간 생활비 공백을 메운다"). 사실 주장을 담지 않는다 — 사실은 항목에.
- 공개 조건: 모든 `slots.policyId`가 `planning`이 있는 공개 항목(카드는 없어도 된다), `caveats` 1개 이상, 모든 claim 검증.
- 견본을 가져오면 `offsetMonths`를 사용자 기준(`baseline`)에 더해 실제 `YYYY-MM`으로 바꾼다(`materialize`). 그 뒤로 견본과 청사진은 따로 산다. 견본이 개정되면 "견본이 바뀌었어요"를 점검 항목으로 띄울 뿐 덮어쓰지 않는다.

## 5. 살아있는 청사진 — 바뀌는 방식

### 5.1 바뀌는 계기

| 계기 | 어디서 아나 | 점검 항목 (`kind`) | 제안하는 수정 |
|---|---|---|---|
| 정책 중요 개정 | 배치의 `policyVersion` < 항목의 material revision | `policy-updated` | 개정 요약 보여 주고 "확인함"(버전 올림) 또는 조정 |
| 정책 종료 | `policy.history`의 `ended` | `policy-ended` | 빼기 / 같은 역할의 다른 항목 후보 |
| 신청 기간 열림·임박 | `applicationState(now)` (기존 `lib/policy-state`) | `window-open` · `window-closing` | 상태를 `ready`로, 신청처 링크 |
| 신청 기간을 지남 | 배치 시점에 확정 회차가 있었고 끝났는데 상태가 `planned`/`ready` | `window-missed` | 다음 회차로 미루기 / `missed` |
| 예상 → 확정 | 예상으로 놓은 시점에 실제 `applications`가 생김 | `schedule-confirmed` | 확정 날짜로 맞추기 |
| 나이 상한 | `baseline.age` + 경과 > `planning.age.max` | `age-limit` | 앞당기기 / 빼기. 나이를 안 적었으면 "확인 필요"만 |
| 중복 수혜 | 두 배치의 기간이 겹치고 `exclusiveWith` | `exclusive-overlap` | 둘 중 하나 고르기 / 기간 나누기 |
| 선행 조건 | `after`의 항목이 앞에 없음 | `missing-prerequisite` | 선행 항목 넣기 |
| 학적·단계 불일치 | 배치 시점의 이정표 단계가 `planning.stages` 밖 | `stage-mismatch` | 시점 옮기기 |
| 항목 비공개 전환 | 항목이 `draft`로 내려감 | `policy-withdrawn` | 빼기 |
| 카드가 새로 생김 | 배치한 항목에 카드가 공개됨 | `card-available` | "따져보기" 안내만. 청사진은 바뀌지 않는다 |
| 견본 개정 | 가져온 path 버전 < 현재 | `path-updated` | 바뀐 칸만 나란히 보여 주기 |
| 사용자 의도 변경 | 목표·이정표 편집 | — | 직접 편집. 이정표를 옮기면 딸린 배치도 함께 옮길지 묻는다 |

점검은 `checkBlueprint(blueprint, policies, paths, now): Check[]` 하나다. 저장하지 않고 열 때마다 계산한다. 테스트는 지금의 `revisit`·`policy-state` 테스트처럼 날짜를 주입한다.

### 5.2 REV — 수락할 때만 오른다

- 제안은 제안일 뿐이다. 사용자가 고른 수정만 쓰인다.
- 쓰기 한 번 = REV 하나. 같은 화면에서 여러 개를 고치면 한 REV로 묶는다.
- 버전 문서: `{ rev, intent, trigger, changes[] }`
  - `trigger`: `{ kind: "user" | "check" | "path" | "ai", checkKind?, policyId? }` — 왜 바뀌었는지
  - `changes[]`: `{ op: "add" | "remove" | "move" | "status" | "milestone" | "goal", targetId, before, after }`
  - `intent`: 사용자가 한 줄 남길 수 있다(선택). 안 남기면 trigger에서 문장을 만든다("청년미래적금 개정 반영").
- REV 비교 화면은 `diffBlueprint`(순수 함수)로 그린다. LLM 없음.
- `status`만 바꾸는 것(신청함 → 받는 중)도 REV를 올린다 — 나중에 "언제 신청했더라"를 볼 수 있게. 비교 화면에서는 상태 변경을 접어 둔다.

### 5.3 시간의 확실성

| 확실성 | 조건 | 그림 |
|---|---|---|
| 확정 | 배치가 **시작하는 달**이 항목 `applications` 회차 안이다 (기간 전체가 아니라 첫 사용만 확정이다) | 실선, ink |
| 예상 | `recurrence`가 `annual`/`rounds`이고 과거 회차로 미뤘다 | 점선, `pending` 색 + "예상" 라벨 |
| 미정 | 근거 없음(`recurrence` 없음), 또는 정책이 그때 있을지 모른다(`once`, 종료 예고) | 점선 회색 + "미정" |

이 구분이 청사진의 정직함이다. 4년 뒤 박사 과정의 지원 정책은 대부분 "예상"이나 "미정"으로 보여야 맞다.

### 6.1 Firestore

```

  status: "active" | "archived"
  rev: number

점검할 것 2                                   ▾
 · 청년미래적금 내용이 바뀌었어요 (v3)   [보기]
 · 국가기술자격 응시료 — 신청 3일 남음  [신청처 ↗]

2026 하반기 ─────────────────────────────
  지금 ▸
  ─ 청년문화예술패스         받는 중    ◆
2027 상반기 ─────────────────────────────
  ● 학부 3학년
  ─ 국가기술자격 응시료      신청 준비  ◆   확정
2027 하반기 ─────────────────────────────
  ┄ 미래내일 일경험          계획       ◆   예상
…
[+ 정책 넣기]  [+ 이정표]        [REV 기록]
```

- 세로 시간축, 반기 단위 띠. "지금" 표시선 하나.
- 이정표는 ● + 굵게, 배치는 선(실선/점선)으로 확실성을 보여 준다(5.3). 상태는 오른쪽 텍스트 라벨 — 색으로 상태를 말하지 않는다.
- ◆ = 따져볼 카드가 있는 정책. 카드 없는 항목에는 표시가 없다.
- 점검 묶음은 접이식, 위에. 없으면 "지금 점검할 것이 없어요" 한 줄.
- 같은 반기에 겹치는 `exclusiveWith` 두 배치는 한 묶음 테두리 + "함께 받을 수 없어요".

### 7.4 배치 상세 (바텀 시트)

```
미래내일 일경험                     [정책 보기 ↗] [따져보기 ◆]
2027 하반기 · 역량 · 예상

왜 여기에   여름방학 인턴형 — 석사 지원 전 연구 외 경력
조건        (항목 claim 칩)
신청        지난 회차 → 다음 회차 예상
한계        (항목 counterpoints 1줄, 있으면)

상태  [계획] [신청 준비] [신청함] [받는 중] [끝남] [놓침] [뺌]
시점  [◀ 반기] 2027 하반기 [반기 ▶]
메모  …

[이 정책 빼기]
```

- 조건·한계는 항목의 claim을 그대로 보여 준다. 시트에서 새 문장을 만들지 않는다.
- `따져보기`는 카드가 있을 때만. 2.5 규칙대로 훅 판단은 건너뛴다.

### 7.5 점검 처리

점검 항목을 누르면 무엇이 바뀌었는지 → 고칠 수 있는 선택지 2–3개 → `[반영하기]`. 반영하면 REV가 오르고 토스트 "REV.5로 저장했어요 · 되돌리기"(5초). 되돌리기도 REV를 하나 더 쌓는다(기록을 지우지 않는다).

`policy-updated`는 카드의 다시 판단하기와 같은 순서를 따른다: 바뀐 내용 먼저 → 내 배치 조정. 카드가 있고 그 카드를 판단한 적이 있으면 다시 판단할지 묻기만 한다(카드 쪽 재평가로 링크).

### 7.6 "+ 정책 넣기"

역할·시점으로 거른 항목 목록(`planning.roles`·`stages`·`age` 기반, 판단 값 사용 안 함). 각 줄은 이름·한 줄 요약·확실성·◆. 목록에 없으면 맨 아래 "찾는 정책이 없나요?" → 주제 한 개를 고르면 빈칸 요청으로 센다(9.4).

### 7.7 REV 기록 `/plan/revisions`

```
REV.5  10월 1일   청년미래적금 개정 반영          점검
REV.4  9월 28일   일경험을 2027 하반기로          직접
REV.3  …
```

한 줄을 누르면 `diffBlueprint` 결과 — 바뀐 배치만 before / after 나란히. 상태 변경은 "상태 변경 3건 ▸"로 접는다. 숫자로 "변화량"을 요약하지 않는다.

### 7.8 모션

새 것 없음. 시트·토스트·목록 떠오름은 로드맵 4.11의 값을 그대로 쓴다. 시간축은 처음 열 때 "지금" 위치로 스크롤만 한다(모션 꺼짐이면 즉시).

## 8. AI (B4 — 결정론 기능이 먼저 자리 잡은 뒤)

두 곳만. 둘 다 지금의 `lib/ask` 방식(claim grounding, 목록에서 고르기, 서버 검증, 한도)을 따른다. 카드의 "AI에게 따져보기"는 그대로다 — 항목의 claim을 합친 `Card`를 보기 때문에 바뀌지 않는다.

### 8.1 초안 제안 — "직접 적기"와 "다시 짜기"

- 입력: 목표 문장, 기준(학적·나이 선택), 지금 청사진(있으면).
- 컨텍스트: **공개 항목의 `planning` 요약 + 핵심 claim 목록**(항목 수십 개면 프롬프트 하나에 들어간다 — 검토 5.4와 같은 판단. 수백 개가 되면 역할·단계로 먼저 거른다). 오늘 날짜와 각 항목의 신청 상태.
- 출력(구조화): `placements: [{ policyId, from, to?, role, why, claimIds }]`, `milestones`, `gaps: string[]`(항목이 없어 비어 있는 필요 — "대학원 등록금 지원 정책이 아직 없어요").
- 서버: 목록 밖 `policyId`·`claimIds` 버림 → `checkBlueprint`로 겹침·나이·선행을 검사 → 위반 배치는 빼고 이유를 붙여 보여 준다.
- 사용자는 제안을 하나씩 넣거나 뺀 뒤 저장. 저장되면 `trigger.kind = "ai"`인 REV.
- 목표 문장은 사용자 상태라 저장하지만, AI 응답 원문은 저장하지 않는다(대화 저장 안 함 유지).

### 8.2 청사진에 묻기

"석사 때 받을 수 있는 생활비 지원은?", "창업 실험을 휴학하고 해도 돼?" — 배치된 항목들의 claim + 청사진 구조로만 답한다. 자격 판정 금지·평가 권유 금지 규칙은 `lib/ask/grounding.ts`의 `SYSTEM_PROMPT`를 그대로 잇는다. 항목 밖이면 "등록된 정책에 없어요" + 빈칸 요청으로 센다(주제 + 횟수만, 질문 원문은 저장하지 않는다).

### 8.3 하지 않는 것

- AI가 청사진을 직접 고치지 않는다. 언제나 제안 → 사용자 수락.
- 주기적 자동 개정 제안 없음. 계기는 5.1의 결정론 점검이다.
- 판단 값·이유를 컨텍스트에 넣지 않는다.
- AI가 항목을 공개하지 않는다. 항목 초안을 AI로 쓰더라도 공개는 사람의 원문 대조 뒤다(9.3).

## 9. 콘텐츠

### 9.1 기존 카드를 두 층으로 나누기

지금 카드 파일 15개(초안 포함)를 같은 id의 항목 + 카드 경험으로 나눈다. 기계적인 이동이다.

| 지금 카드 필드 | 가는 곳 |
|---|---|
| `audience` · `category` · `lifeStages` · `shortTitle`(→`name`) · `claims` · `sources` · `counterpoints` · `policy` · `revisions` · `reviewedAt` · `links` | 항목 |
| `hook` · `shorts` · `flow` · `reasonOptions` · `game` · `reveal` · `suggestedQuestions` · `tone` | 카드 |
| `publishStatus` | 둘 다 — 지금 값을 양쪽에 |
| (새로) `summary` · `planning` | 항목 — 새로 쓴다 |

완료 확인: 나누기 전후 `CARDS`를 직렬화해 비교하면 같아야 한다(테스트 한 번). 화면·API·판단 기록이 바뀌지 않는다.

### 9.2 지금 항목으로 쓸 수 있는 것

| 항목 (지금 카드) | 박사 경로 | 창업 경로 | 역할 |
|---|---|---|---|
| `exam-fee-support` 국가기술자격 응시료 | ○ | ○ | 역량 |
| `work-experience` 미래내일 일경험 | ○ | ○ | 실험 |
| `youth-challenge` 청년도전지원사업 | | | 공백기 안전망 |
| `youth-monthly-rent` 청년월세 | ○ | ○ | 주거 |
| `young-future-savings` · `youth-tomorrow-savings` · `youth-housing-dream-account` | ○ | ○ | 자산·주거 (`exclusiveWith` 확인 대상) |
| `everyone-transit-card` · `youth-culture-pass` | ○ | ○ | 생활 |
| `youth-job-leap` 청년일자리도약 | | | 취업 경로 |

### 9.3 새 항목 — 두 경로를 빈칸 없이

넓게가 아니라 두 경로를 깊게. 경로마다 필요한 항목을 15–20개로 보고, 9.2의 약 10개를 빼면 경로당 10개 안팎을 새로 쓴다. 아래는 이름만이다 — 사실·금액·조건은 항목을 쓸 때 원문에서 확인한다.

- 박사 경로: 국가장학금, 취업 후 상환 학자금 대출, 이공계 대학원생 연구생활장려금, 대학원 연구 인력 지원 사업(BK21 등)
- 창업 경로: 대학 학생 창업 지원, 예비창업패키지, 청년창업사관학교, 청년 창업 세액 감면, 재도전 지원
- 공통: 청년 전월세 대출, 청년 공공주택 — 주거가 경로의 큰 변수라서

항목 쓰는 순서: 공고 원문을 모은다 → (선택) AI로 claim·`planning` 초안 → `pnpm review` 대조 목록 → 원문과 대조해 `verified: true` → 공개. AI 초안은 품을 줄이는 도구일 뿐 검증을 대신하지 않는다.

### 9.4 승격과 빈칸

- **카드로 승격**: 청사진 배치 수(운영 내부 집계, 30명 이상일 때만 봄)와 빈칸 요청 수가 많은 항목, 그리고 따져볼 거리(논쟁·비판 자료)가 있는 항목부터. 승격은 같은 id로 카드 경험 파일 하나를 더하는 일이다 — 항목은 손대지 않는다.
- **빈칸 요청**: "+ 정책 넣기"의 "찾는 정책이 없나요?"와 AI `gaps`를 주제별 횟수로만 센다. `pnpm metrics`에 한 표로 보인다. 다음에 쓸 항목의 순서를 여기서 정한다.

### 9.5 견본 첫 두 개

1. **이공계 박사 진학 — 학부 3학년부터** (`degree`)
2. **재학 중 창업 실험 → 졸업 후 창업** (`startup`)

두 견본이 공개 조건(모든 칸이 공개 항목, caveats 1개 이상)을 채우기 전까지 청사진은 "직접 만들기 + 지금 항목"으로만 연다.

검토 문서 3장에 더하는 것만.

| # | 리스크 | 조치 |
|---|---|---|
| 1 | **잘못된 계획으로 기회를 놓침** — 몇 년 뒤 정책을 확정처럼 믿는다 | 확실성 3단계를 화면에서 숨길 수 없게(5.3). 시간축·정책 페이지 머리에 "공식 공고로 다시 확인하세요" 상시. 자격은 "가능성 / 확인 필요"만 |

| 4 | **정부 홍보로 읽힘** — 카드보다 가벼운 항목이 늘면 "혜택 목록"으로 보이기 쉽다 | 견본마다 `caveats`(경로의 기회비용·정책 중단 위험)를 출처와 함께 1개 이상 요구. 항목에 비판·한계가 있으면 정책 페이지와 배치 시트에 함께 보인다. 혜택 합계 금액 표시 금지(원칙 5). `/about`에 항목과 카드의 차이를 적는다 — 항목은 사실 정리, 따져보기는 카드에서 |

**청소년 트랙**: 고교 → 대학 진학 청사진은 수요가 크지만, 청소년의 계획 기록을 서버에 두는 문제가 남는다. B단계 동안 청사진은 `young_adult`만. 청소년은 이후 "기기에만 저장" 모드로 검토한다(정책 평가와 같은 방식). 청소년 대상 항목(정책 페이지)은 지금 청소년 카드와 같은 기준으로 연다.

## 11. 단계

각 단계는 따로 배포할 수 있다. 로드맵 M7(PWA·알림)과는 B5에서 만난다.

### B0 · 콘텐츠 두 층

1. `policySchema`·`planningSchema` + `validatePolicy`·`validatePolicies`(대칭·순환·존재) + `validateCard(card, policy)`
2. 기존 카드 15개를 항목 + 카드 경험으로 나누기, `resolveCard` (9.1)
3. 기존 항목에 `summary`·`planning` — claim 검수 포함
4. 검증·검수 스크립트를 항목까지 넓히기

완료 기준: 나누기 전후 `CARDS`가 같다(테스트). `pnpm check` 통과. `exclusiveWith`가 한쪽에만 적히면 실패한다(테스트). 이 단계만 배포해도 사용자에게 보이는 변화가 없다.

**상태 (2026-10-01)** — 1·2·4 완료, 3은 일부.
- 카드 15장을 같은 id의 항목(`src/content/policies`) + 카드 경험(`src/content/cards`)으로 나눴다. 주석은 줄 단위로 옮겨 그대로 남겼다. 나누기 전후 `ALL_CARDS`를 직렬화해 비교해 같음을 확인했다(일회성 확인 — 스냅숏은 저장소에 두지 않는다). `pnpm check`·`pnpm test:emulator`·`pnpm build` 통과.
- 두 스키마 모두 모르는 필드를 거절한다 — 카드에 claim을 적거나 항목에 훅을 적으면 `pnpm validate`가 멈춘다.
- `planning`: 청년 항목 10개에 채웠다. claim 문장이 그대로 말하는 값만 옮겼다 — 나이·기간이 claim에 없거나 조건부면(모두의카드 청년 유형, 문화예술패스 출생연도 기준, 일자리도약 수도권 유형) 두지 않았다. 다음 회차 근거가 claim에 있는 것은 청년미래적금(회차 모집) 하나뿐이라 나머지는 `recurrence`가 없다(미정). `exclusiveWith`는 근거 claim이 있는 쌍이 아직 없다. **이 값들은 편집자 대조 전이다** — `pnpm review` 목록의 `계획 정보` 표시로 확인한다.
- 스키마 조정: `recurrence`를 선택으로(근거 없으면 미정), 역할에 `employment`(취업·근속)·`living`(교통·문화) 추가 — 9.2 표가 이미 쓰던 역할이다.
- `summary`는 아직 없다(경고). 정책 페이지(B1)와 함께 쓴다. 청소년 항목 5개는 청사진 대상이 아니라 `planning`을 두지 않는다.

### B1 · 새 항목과 정책 페이지

1. `/policy/{id}` 정책 페이지 + `seenFacts`와 카드 훅 판단 건너뛰기(2.5)
2. 9.3 새 항목 — 박사·창업 경로에 필요한 것부터, 원문 대조 후 공개
3. 경로 견본 스키마 + 견본 2개(draft → 공개)
4. 주제 페이지에 "카드가 아직 없는 정책" 묶음, sitemap에 공개 항목

완료 기준: 두 견본의 모든 칸이 공개 항목이다. 정책 페이지를 연 뒤 같은 정책의 카드를 열면 훅 판단 없이 게임부터 시작한다.

**상태 (2026-10-01)** — 1·3·4 완료, 2는 초안까지. 견본 공개는 편집자 대조 뒤.
- 정책 페이지 `/policy/{id}`: 사실(claim 칩)·신청 상태·"계획할 때 볼 것"(planning)·비판과 한계·원자료·정정 요청. 카드가 있으면 `따져보기`. 초안은 "초안 — 원문 대조 전"으로 표시. 운영 빌드는 공개 항목만 만든다.
- 사실을 먼저 본 사람(2.5): 정책 페이지가 `seenFacts`(브라우저 저장소)에 기억하고, 카드는 훅 신뢰와 훅 정확도를 둘 다 건너뛴다(6단계 → 5단계, 브라우저에서 확인). 지표는 `card_open_informed`를 따로 보내 첫 판단 도달률 분모에서 뺀다. 개인정보처리방침에 한 줄 더했다.
- 정정 요청은 항목 기준으로 받는다 — 카드 없는 항목에서도 보낼 수 있다. 문서 필드 이름(`cardId`·`cardVersion`)은 그대로.
- 주제 `startup`(창업) 추가 — 관심 주제 상한을 주제 수에 맞췄다. 주제 페이지 아래 "카드가 아직 없는 정책", sitemap에 공개 항목.
- 새 항목 8개(모두 초안, claim 검증 전): 국가장학금 Ⅰ유형, 취업 후 상환 학자금대출, 이공계 연구생활장려금, 4단계 BK21 / 학생 창업유망팀 300+, 예비창업패키지, 청년창업사관학교, 청년창업중소기업 세액감면. 출처는 정책브리핑·한국장학재단·한국연구재단·기업마당·국가법령정보센터를 먼저 쓰고, 정부 원문을 찾지 못한 두 가지(연구생활장려금 2026 참여 대학 수, 학생 창업유망팀)는 보도다. 출처끼리 숫자가 다르거나 원문에서 숫자를 확인하지 못한 것(예비창업패키지 사업화 자금, 세액감면 2026년 이후 감면율·청년 나이 요건, 학자금대출 생활비 한도)은 적지 않았다.
- 경로 견본: `path-schema.ts`(검증은 칸의 역할·단계가 항목 planning과 맞는지까지 본다 — 연구생활장려금을 학부 시점에 두면 실패), 견본 2개 `phd-stem`·`startup-in-college`(초안, caveat 2개씩). 역할에 `startup`(창업 준비·운영) 추가.
- 남은 것: 편집자 원문 대조(`pnpm review`) → 항목 공개 → 견본 공개. 박사 경로는 `exam-fee-support`(초안 카드)도 공개되어야 한다.

### B2 · 청사진 만들기와 보기

1. `lib/blueprint` model·materialize·certainty·apply·diff + 단위 테스트
2. `/api/blueprint` + `saveBlueprint` 트랜잭션 + 규칙 + 규칙 테스트
3. `/plan/new`(3단계) · `/plan`(시간축) · 배치 시트 · "+ 정책 넣기"
4. 삭제·내려받기에 청사진 포함

완료 기준: 견본에서 REV.1을 만들고 상태를 바꾸면 REV.2가 남는다. 다른 사람의 청사진을 읽을 수 없다(규칙 테스트). 확정/예상/미정이 날짜를 바꿔 넣은 테스트에서 맞게 나온다. 390px에서 시간축 가로 스크롤 없음.

**상태 (2026-10-01)** — 완료. 완료 기준 네 가지 모두 확인(단위·에뮬레이터 테스트, 브라우저 390px).
- `lib/blueprint`: `month`(YYYY-MM 계산·반기) · `model`(스키마·상태 전이 표·상한) · `materialize` · `certainty` · `apply`(op 목록 → 다음 모습, 거절 코드) · `diff` · `timeline`(반기 묶기). 단위 테스트 25개.
- 쓰기: 클라이언트는 op 목록만 보낸다. 서버(`server/blueprint-store`)가 트랜잭션에서 `applyChanges`로 다음 모습을 만들고, 변경 로그는 앞뒤 모습의 `diffBlueprint`로 만든다 — op마다 따로 적지 않아 로그와 실제가 어긋날 수 없다. `expectedRev`가 다르면 `stale-rev`(409)로 거절, 바뀐 것이 없으면 `no-change`로 REV를 올리지 않는다. 지운 선택 필드는 저장 때 빠진다.
- 만들기는 청년만, 프로필이 있어야 한다. 활성 청사진 1개 — 보관(`DELETE`)하면 새로 만들 수 있다. 기준 달은 서버의 오늘.
- 화면: `/plan/new`(견본·직접 적기 → 학적·만 나이·목표 연도 → 초안 미리보기와 경로의 한계 → 저장), `/plan`(목표·REV, 상시 안내, 반기 시간축, 배치 시트 — 상태·반기 이동·메모·빼기, 정책 넣기 — 역할로 거르기·시작 달·개월 수·이정표, 이정표 넣기·고치기, 목표 바꾸기, 보관). 견본은 마지막 칸이 든 해보다 목표 연도를 이르게 잡지 못한다.
- 읽기는 `/plan` 화면에서만 구독한다(`useActiveBlueprint`) — 앱 전체 구독에 얹지 않는다.
- 규칙: `blueprints`·`versions` 본인 읽기만, 쓰기는 모두 닫음(규칙 테스트). 계정 삭제가 함께 지운다(에뮬레이터 테스트). 내려받기에 청사진과 REV 기록을 넣었고, 개인정보처리방침에 한 줄 더했다.
- 확실성 규칙을 고쳤다(5.3): 기간 중 한 달이라도 회차와 겹치면 확정으로 보던 것을, 시작 달이 회차 안일 때만 확정으로. 8년짜리 대출 배치가 "확정"으로 보이던 것을 브라우저에서 발견했다.
- 운영 빌드에서는 견본 둘이 초안이라 `/plan/new`에 "직접 적기"만 뜨고, 공개 항목만 넣을 수 있다. 진입점(피드·내 기록·카드 끝 화면)은 B3.

### B3 · 살아있는 점검과 연결

1. `checkBlueprint` — 5.1 표의 전부, 날짜 주입 테스트
2. 점검 묶음 UI + 처리 흐름(7.5) + `ackedChecks`
3. `/plan/revisions` + diff 화면
4. 카드 끝 화면·정책 페이지의 "청사진에 넣기", 피드·내 기록 진입점

완료 기준: 항목에 material revision을 하나 더하면 그 항목을 배치한 청사진에 `policy-updated`가 뜨고, 반영하면 REV가 오르고 점검이 사라진다. 카드 한 장을 끝내고 두 번 탭 안에 청사진에 넣는다.

### B4 · AI와 승격 신호

1. 초안 제안(8.1) — 구조화 출력, 서버 검증, 한도는 `lib/ask/limits` 공유
2. 청사진에 묻기(8.2)
3. 빈칸 요청·배치 수 → `pnpm metrics`의 승격 후보 표(9.4)

완료 기준: 목록 밖 policyId·claimId가 저장되는 경로가 없다(테스트). 판단 값이 프롬프트에 들어가지 않는다(테스트).

### B5 · 알림 (M7 이후)

`window-closing`·`policy-updated`·`window-missed` 세 가지를 M7 알림 설정에 항목 하나("내 청사진 점검")로 더한다. 기본 꺼짐. 문구에 정책명과 기간만 — 상태·메모·목표를 담지 않는다.

## 12. 결정이 필요한 것

| 항목 | 선택지 | 기본 제안 |
|---|---|---|
| 콘텐츠 층 | 카드만 / 항목 + 카드 | **결정(2026-10-01): 항목 + 카드** |
| 카드 없는 항목의 공개 조건에 비판·한계 | 필수 / 선택 | 선택. 견본 `caveats`는 필수 |
| 사실을 먼저 본 사람의 카드 | 훅 판단 건너뜀 / 그대로 묻고 표시 / 그대로 | 건너뜀 (2.5) |
| 시점 정밀도 | 월 / 반기 / 학기 | 저장은 월(`YYYY-MM`), 화면은 반기 띠 |
| 활성 청사진 수 | 1 / 2(경로 비교) | 1로 시작, 상한 상수만 둔다 (도장과 같은 판단) |
| 나이 받기 | 안 받음 / 만 나이 선택 입력 / 생년 | 기준 시점 만 나이, 선택 |
| 혜택 금액 합계 | 보여 줌 / 안 보여 줌 | 안 보여 줌 (원칙 5) |
| 상태 변경도 REV인가 | 예 / 아니요 | 예, 비교 화면에서는 접는다 |
| 청사진 공유 | 없음 / 견본 링크만 / 개인 청사진 이미지 | 견본 링크만. 개인 청사진은 민감 사정이 드러날 수 있다 |
| 청소년 진학 청사진 | 지금 / 기기 저장 모드로 나중 | 나중 (10장) |
| 탭 구조 | 머리 링크 / 하단 탭 신설 | 머리 링크로 시작. 청사진 사용률이 내 기록을 넘으면 하단 탭 검토 |

## 13. 하지 않는 것

자격 확정 판정, 혜택 합계·달성률·랭킹, 다른 사람 청사진 보기·팔로우·댓글, 판단 값을 쓰는 정책 추천, 항목 밖 정책(AI가 만든 정책 포함), AI의 자동 개정, AI의 항목 공개, AI 대화 저장, 소득·장애·건강 정보 수집, 피드에 카드 없는 항목 넣기.
